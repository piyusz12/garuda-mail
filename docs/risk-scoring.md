# GARUDA (SIH26159) — Cryptographic Risk Scoring & AI Anomaly Methodology

## 1. Core Principle: Separation of Three Independent Measurements

GARUDA Sentinel enforces a strict architectural boundary between three fundamentally different security measurements. **AI anomaly detection NEVER overrides or suppresses confirmed deterministic policy findings.**

```
+-----------------------------------------------------------------------------------+
|                       THREE INDEPENDENT SECURITY METRICS                          |
+-----------------------------------------------------------------------------------+
|                                                                                   |
|  [ 1. Cryptographic Risk Score (CRS) ]                                            |
|  - SOURCE: Deterministic Policy Engine (Rule-based)                               |
|  - SCALE: 0 to 100 (Higher = Greater Cryptographic Risk)                          |
|  - BASIS: Severity of findings, standards compliance (NIST/PCI), asset exposure   |
|                                                                                   |
|  [ 2. AI Anomaly Score ]                                                          |
|  - SOURCE: Unsupervised Machine Learning (Isolation Forest / Autoencoder)         |
|  - SCALE: 0 to 100 (Higher = More Unusual relative to normative network baseline) |
|  - BASIS: Statistical deviation in continuous features (packet entropy, timing)   |
|                                                                                   |
|  [ 3. Evidence Confidence ]                                                       |
|  - SOURCE: Forensic Data Completeness Metric                                      |
|  - SCALE: 0 to 100% (Higher = More complete observable evidence)                  |
|  - BASIS: Handshake visibility, TCP stream completeness, packet counts            |
|                                                                                   |
+-----------------------------------------------------------------------------------+
```

## 2. Metric A: Cryptographic Risk Score (CRS)

The Cryptographic Risk Score is a deterministic, explainable measurement of cryptographic exposure.

### 2.1 Mathematical Formulation
$$\text{CRS} = \min\left(100, \max\left(0, \sum_{i \in \text{Findings}} W(S_i) \cdot E_i \cdot C_i\right)\right)$$

Where:
- $W(S_i)$ is the Base Severity Weight:
  - **CRITICAL:** 35 points (e.g. Plaintext credentials, TLS 1.0, Expired certificate)
  - **HIGH:** 20 points (e.g. Missing forward secrecy, weak 3DES/RC4 cipher)
  - **MEDIUM:** 10 points (e.g. Certificate expiring in 30 days, Quantum-vulnerable KEX)
  - **LOW:** 4 points (e.g. Suboptimal ALPN or extension preference)
  - **INFORMATIONAL:** 0 points
- $E_i$ is the Asset Exposure Multiplier:
  - External / Internet-facing endpoint: $1.2$
  - Internal LAN / DMZ endpoint: $1.0$
  - Isolated test harness: $0.8$
- $C_i$ is Evidence Confidence ($0.0$ to $1.0$).

## 3. Metric B: AI Anomaly Score

The AI Anomaly Score is generated by an unsupervised machine learning model (Isolation Forest) trained on normative baseline features.

### 3.1 Feature Vector Representation
1. `tls_version_ordinal`: Encoded version (SSL3=0, TLS1.0=1, TLS1.1=2, TLS1.2=3, TLS1.3=4).
2. `cipher_suite_entropy`: Shannon entropy of proposed cipher suite ordering.
3. `extension_count`: Number of advertised TLS extensions.
4. `stream_duration`: Total TCP flow duration in seconds.
5. `byte_transfer_ratio`: Client-to-server vs server-to-client payload ratio.
6. `forward_secrecy_binary`: Boolean flag (1 for PFS, 0 for static RSA).

### 3.2 Output Interpretation
- **0–39 (Normal):** Observed traffic matches learned enterprise communication baselines.
- **40–69 (Unusual):** Statistically uncommon extension or cipher combinations; warrants operational review.
- **70–100 (Highly Anomalous):** Significant structural deviation (e.g. automated beaconing tools or legacy downgrade behavior).

---

## 4. Metric C: Evidence Confidence

Evidence Confidence measures whether the capture provided sufficient packet data to justify the conclusions.

$$\text{Confidence} = 100 - \left(P_{\text{missing}} \cdot 30 + P_{\text{encrypted\_cert}} \cdot 15 + P_{\text{truncation}} \cdot 25\right)$$

- **90–100%:** Complete bidirectional TCP stream with visible ClientHello and ServerHello.
- **60–89%:** Partial capture (e.g. TLS 1.3 handshake where certificates are encrypted).
- **< 60%:** Heavily truncated capture or dropped packets; findings marked with **Insufficient Evidence** qualifier.
